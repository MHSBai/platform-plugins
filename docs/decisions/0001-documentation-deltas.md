# 0001. Deltas between the plugin documentation and Design v2.1

Status: accepted, 2026-11-03 (Stage 1). Rule applied: where the documentation disagrees with the design, the documentation governs.

Sources fetched 2026-11-03: claude.com/docs/plugins/overview, code.claude.com/docs/en/plugins/create-marketplace, claude.com/docs/plugins/platform-support, claude.com/docs/plugins/submit, code.claude.com/docs/en/plugins/manifest-reference; and, because those pages defer to them for field rules, code.claude.com/docs/en/plugins/marketplace-reference, code.claude.com/docs/en/skills (frontmatter reference), code.claude.com/docs/en/plugins/components and code.claude.com/docs/en/plugins/host-marketplace.

| # | Design or prompt | Documentation | Resolution |
|---|---|---|---|
| 1 | SKILL.md frontmatter carries `register`, `connector` and `pack` as top-level keys. | Claude Code ignores unknown frontmatter keys without error. claude.ai skill uploads and the Skills API accept only `name`, `description`, `license`, `compatibility`, `metadata` and `allowed-tools`, and fail on any other key. `metadata` is the documented place for tooling data. | `register`, `connector`, `pack` and `triggers` sit under `metadata`. Lint rule L03 rejects any top-level key outside the six. |
| 2 | Trigger phrases per command. | No trigger field exists. `description` (with `when_to_use`, Claude Code only) is what routing reads; the combined text is truncated at 1,536 characters. | Phrases live in `catalog/manifest.yaml` and `metadata.triggers`, and are repeated in prose inside `description` so that routing sees them on every surface. Descriptions are capped at 1,024 characters by L03 (the Agent Skills limit). |
| 3 | Commands written as `/brief`, `/letter`. | Every plugin skill is namespaced: `/mhsb-operations:brief`. In chat, a skill is selected from plain language or the `/` menu. | The short form remains the catalog's name. Collisions are impossible at runtime across plugins, but the design's rule is kept: L09 rejects a duplicate short name in any combination, because staff use the short form. |
| 4 | "License reference" in plugin.json. | `license` takes an SPDX identifier. | Core: `Apache-2.0`. All others: `LicenseRef-MHSB-Source-Available`, the SPDX form for a license outside the list, with the text in `LICENSE-SOURCE-AVAILABLE.md`. |
| 5 | Version 0.1.0 per plugin. | When both the marketplace entry and plugin.json set `version`, plugin.json wins and validate warns. | `version` is set in plugin.json only; marketplace entries omit it. L02 rejects an entry that repeats it. |
| 6 | Marketplace and directory sources pinned to tags. | Relative-path entries resolve inside the marketplace checkout; the catalog itself is pinned when users add `MHSBai/platform-plugins#<tag>`. `ref` and `sha` apply only to `github`, `url` and `git-subdir` sources. | Entries use relative paths under `plugins/`. Tag pinning is done at the add command (`#v0.1.0`), as recorded in docs/release.md. |
| 7 | "No bin". | A top-level `bin/` makes chat and Cowork refuse the whole plugin. | Consistent with the design. L13 rejects `bin/`, and also hooks, agents, commands, monitors, LSP servers, output styles, themes, workflows and `settings.json`. |
| 8 | Bundled connectors at mcp.mhsbsolutions.com. | A remote `http` server with a fixed URL loads on every surface; in chat it is listed on the plugin's Connectors tab and works once added and connected; on Team and Enterprise an Owner adds it. | `.mcp.json` uses `{"mcpServers": {"mhsb-<name>": {"type": "http", "url": ...}}}` with no `${user_config}` reference (a reference in the URL is ignored in chat). L13 rejects any other server shape. |
| 9 | Practice packs contain no skills. | A plugin with no components is valid; nothing loads into Claude. | Packs are plugins carrying data for the service (fragment and templates). Their value reaches the session through the firm connector and the Firm Profile, not through the plugin loader. |
| 10 | MyCase plugin: vocabulary and mapping only. | Same as 9. | `mhsb-mycase` carries no commands and no connector in 0.1.0; vocabulary files arrive with Stage 3. |
| 11 | Directory submission for the core. | The directory reads `icon`, `documentationUrl`, `supportUrl`, `privacyPolicyUrl` and `termsOfServiceUrl` from plugin.json; these are errors in a marketplace entry. | Not set in 0.1.0; the privacy policy and terms do not exist yet (Stage 14). The schema permits them in plugin.json and forbids them in entries. |
| 12 | Unknown keys. | Unknown top-level plugin.json and marketplace keys are stripped with a warning. | The lint schemas treat them as errors, which is stricter and loses nothing. |
| 13 | Supported combinations: core plus operations plus one platform plugin. | (Commercial, not documentation.) Design Section 3 does not sell operations to MyCase firms in version 1. | The generator enumerates MyCase with operations anyway, so the lint covers the largest set the manifest allows. The figure is 19 commands, below the cap. |
